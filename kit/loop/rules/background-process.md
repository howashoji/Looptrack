# 背景プロセスの規律（終わらない子プロセスを作らない）

> kit/loop の rules です。ペア: Stop `stop-runaway-background-process.sh`（セッションが起こした長時間の子プロセスを検知してやり直しを求める）。

## 要点
<!-- looptrack:inject session codex copilot -->

- 背景でループを実行するときは必ず上限（最大試行回数か締切）を持たせます。超えたら理由を付けて諦め、報告してください。無限の `until` / `while` は書きません。
- 待つ対象は消えない識別子で選びます。CI は PR の番号で見ます。force-push で消える SHA は待ちません。使い終わった背景プロセスは止めます。
- 背景で待つ作業をサブエージェントに出すときは**上限の一文を指示文にそのまま書き写します**。この規律は親にしか注入されないからです。待ち始める前に待機対象があるかも確かめさせてください。

## 背景ポーリングの鉄則

完了マーカーや CI の完了を待つために背景でループを実行するなら**必ず上限を持たせます**。

- **無限の `until` / `while` を書かないでください。** 最大試行回数か締切のどちらかを必ず持ちます。超えたら**理由を付けて諦めて報告します**。黙って回り続けてはいけません。
- **待つ対象は消えることもある前提で選びます。** CI 待ちは PR の番号のような消えない識別子で見ます。
  コミットの SHA を待っていると、rebase と force-push でそのコミットが消えた時点で終了条件は二度と成り立ちません。
- サブエージェントにポーリングさせるときも同じです。親がブランチを書き換えると子が待っている対象が消えます。
- 使い終わった背景プロセスは止めます。

> 実例: サブエージェントが仕掛けた無限ポーリング 2 本が 15 時間以上動き続けて外部 API をおよそ 6,400 回呼びました。
> 待っていたのは親が force-push で消した SHA です。**サブエージェントの一覧にも worktree の一覧にも出ず利用者の画面でしか見えませんでした。**

## サブエージェントへ出すときに書き写す一文

この規律は **rules として親セッションに注入されるだけです。サブエージェントへの指示文には自動では入りません**。
親が書き写さない限り子は上限の無い待ちループを当たり前のように書きます。
子は待機対象が途中で消えることも、着手した時点で既に終わっていることも知らないまま待ち始めます。

**実測では 1 日で上限の無い `until` ループが 3 本作られました。**
2 本は待っていた作業が既に終わっていました（人が `ps` で見つけて kill しました）。
残る 1 本は**待っていたパスがそもそも存在しませんでした**（`ls` で確認）。終了条件は決して成り立たず
親のセッションが終われば孤児プロセスとして残り続けるところでした。
**3 本とも人が `ps` で見つけたもので Stop hook の閾値（既定 30 分）には達していませんでした。**
この規律の本文には以前から「15 時間・外部 API を約 6,400 回」の実例が書いてあります。
**それでも同じ日に 3 本作られた**ので、規律を本文に置くだけでは足りません。**指示文に書き込みます。**

**背景で何かを待たせる作業をサブエージェントに出すときは次の 3 行を要約せずにそのまま指示文に入れてください。**

```text
背景で待つループを書かない。待つ必要があるなら、最大試行回数か締切を必ず持たせ、超えたら理由を付けて諦めて報告する。
待つ対象は、待ち始める前にその場で存在を確かめる（無ければ待たずに、その時点で報告する）。
使い終わった背景プロセスは自分で止め、報告に「起こした背景プロセスと、その停止」を 1 行で書く。
```

**Claude Code ではこの 3 行を `pre-tool-subagent-bound`（PreToolUse）が指示文に自動で追記します**。
先頭には固定の印 `[looptrack:background-bound]` が付きます。印が既にある指示文には足さず呼び出しを止めることもしません。
**ほかの AI では自動では入らない**ので、親が上の 3 行をそのまま書き写します。どの AI で効くかは kit の README を見てください。

親は受け取った報告で**背景プロセスを止めたところまで確かめてから統合します**。報告にその 1 行が無いときは
統合の前に `ps -eo pid,ppid,etime,command | grep -E 'until|while' | grep -v grep` で自分で確かめます。残っていれば kill してください。

## 検知（起動前・子の終了直後・ターンの終わり）

- **起動前**（PreToolUse の `pre-tool-wait-loop-guard`）: 上限の無い待ちループを `deny` で止めます。`until` / `while` のループ本体に `sleep` があり
  上限の式が無いものです。上限の式とは `break`・`timeout`・`seq`・`SECONDS`・`date +%s`・数の比較（`-ge` `-gt` `-le` `-lt`）・
  `--max` などです。止められたら理由に示された書き直し方（最大回数・締切・`timeout`）のどれかに直せば通ります。例外は
  `LOOPTRACK_LOOP_WAITLOOP_ALLOW`（空白区切り）で指定します。**上限はあっても待つ先の親ディレクトリが無い**ときは止めずに注意だけを返します。
  まだ無いファイルができるのを待つのは正しい使い方だからです。
  前置の語や `eval` で包んだ待ちループ（`sudo sh -c '…'`・`nohup bash -c '…' &`・`setsid sh -c '…'`・`time while …`・
  `eval "while true; …"`・`sudo -u deploy sh -c '…'`）も止めます。前置の語と入れ子のほどき方は git ガード・秘密のガードと同じ処理です。
  **それでも捕まえられるのはうっかりミスだけです**。一覧に無い前置の語（`caffeinate bash -c '…'`）と引数の位置
  （`ssh host bash -c '…'`・`docker run img bash -c '…'`）は確認されずに通ります。そこを拾うのは下の経過時間による検知だけです。
- **子の終了直後（SubagentStop）とターンの終わり（Stop）**: `stop-runaway-background-process` が見ます。
  対象はコーディング AI が Bash ツールのために起こしたシェル（`bash -c` / `zsh -c` とシェルのスナップショット）のうち、閾値（既定 30 分）より長く生きているものです。
  **上限の無い待ちループの形をしたシェルだけは閾値が短く**既定で 10 分です（`LOOPTRACK_LOOP_RUNAWAY_LOOP_THRESHOLD_MIN`）。ほかは 30 分のままです。
- MCP サーバ・dev サーバ・docker・エディタなどは正当に長く動くので対象から外します。プロジェクトで長く動くものは
  `LOOPTRACK_LOOP_RUNAWAY_ALLOW`（正規表現）で足してください。閾値は `LOOPTRACK_LOOP_RUNAWAY_THRESHOLD_MIN` で変えられます。
- やり直しを求められたら次のどれかにします。不要なら kill する / まだ必要なら上限を持つ形に書き直す / 正当に長く動かす必要があるなら理由を記録して続ける。
