# 作業規律（全作業共通）

> kit/loop の rules です。利用者が繰り返し伝えてきた指示や指摘を、スタックに依らない行動規律としてまとめました。
> SessionStart `session-start-rules.sh` が「全作業共通の規律」節を、UserPromptSubmit `user-prompt-rules.sh` が
> 「毎ターンの要点」節を注入します。hook 側に文言を複製しないでください。
> 末尾の「任意節」は注入しません。プロジェクトの事情に合うものだけをプロジェクト側の rules に写して使ってください。

## 毎ターンの要点
<!-- looptrack:inject prompt -->

[作業規律] 事実は live 値・実ファイルで裏取りします（記憶や過去の要約を鵜呑みにしない）/ 着手前に全経路・全関連文書を洗い出します / 完了は実証で示します（grep だけで完了にしない。「緑」には SHA・作業ツリー・キャッシュを使わずに実行したか・所要時間・SKIP 件数・並走本数を添える）/ 先送り・スキップはしません（見つけた課題はその場で起票する）/ 親のコンテキストは判断に使い、手順の決まった作業（調査・実装・テスト・マージ・起票・文書の編集・記録）はサブエージェントに出します（報告には行数の上限を付ける）。詳細は rules の working-discipline.md にあります。

## 全作業共通の規律
<!-- looptrack:inject session -->

利用者が繰り返し伝えてきた指示や指摘をまとめた最優先の行動規律です（全文は rules の working-discipline.md）。

### 応答・進行
- **言行一致**: 「続けます」のようなこれからの宣言には同じターンのツール呼び出しを付けます。作業の途中でツール呼び出しの無いまま終わらないでください。
- **ツール呼び出しはメッセージの冒頭に置きます**（→ output-discipline.md）。
- **先送り・スキップはしません**: 「別セッションで」「別イシュー推奨」で逃げないでください。その場で実行するか、その場でイシューとして起票・記録します。
- **タスクモード契約**: 「確認して」系の依頼は調査報告と計画の提示で止めます。「実行して」系は成果物が完成するまで進めます（`user-prompt-task-mode.sh` が判定・注入し、`pre-edit-task-mode-guard.sh` が確認モード中の編集を止めます）。

### 事実認定（最重要）
- **事実は一次情報で裏取りします**（実ファイル・実データ・live 値・利用者がはっきり言ったこと）。過去の要約・記憶・伝聞を鵜呑みにしないでください。
- **着手前に全経路・全関連文書・全利害関係者を洗い出します**。漏れを 1 つずつ見つけては着手し直すという進め方はしません。
- **grep の範囲の盲点に気をつけてください**: 表記ゆれ（送り仮名・漢字 / かな・英日混在・全角半角）があると検索は空振りします。監査では表記ゆれも含めて確かめます。

### 検証・完了
- **完了は実証で示します**: 実行結果・生成物の実在・実際の本文の引用・観点ごとの合否。grep の結果だけで「完了」にしないでください。
- **確かめていない推測を確定した事実として書きません**。確度が低いものは「要確認」と明示して確認先（誰に・どの資料で）まで書きます。
- **成果物は読み手が判断できる状態になって完了です**（背景・前提・決定事項・未決事項がそろっている）。
- **決定事項と未決事項は分けて記録します**。未決には「誰が・いつまでに・何を決めるか」を添えてください。
- **共有の作業ツリーで取った検査の緑はその SHA の根拠になりません。** 検査の途中でほかのセッションがマージすると
  HEAD が動き、テストが途中から別のファイルを読むからです。実例として本体の作業ツリーで「全テスト PASS」と報告した SHA を
  別のセッションが固定して検査したら e2e が 3 件 FAIL しました。壊れた状態の push は止まりました。ただ、それまでの「全検査 PASS」の
  連絡もすべて同じやり方で、その SHA を見ていた保証はありませんでした。**検査はその SHA を固定した場所で行います。**
  ```sh
  SHA=$(git rev-parse --short HEAD); git worktree add --detach ../verify-$SHA $SHA   # この中で全検査を回す
  git push origin $SHA:main    # 本体の HEAD が進んでいても、検査した SHA だけが出る
  git worktree remove ../verify-$SHA   # 検査用の作業ツリーは毎回消す
  ```
- **「緑」を人に伝えるときは、どの SHA をどこ（固定した作業ツリー）で検査したかを明記します。**
  **落ちたテストを「フレークだろう」で片付けないでください**。なぜ確定的にその結果になるのかを経路で示すまでは環境のせいにしません。
- **「緑」の報告には、SHA と作業ツリーに加えて「キャッシュを使わずに実行したか・所要時間・SKIP の件数・並走本数」を必ず添えます。**
  欠けていたら受け取った側は根拠として扱いません。正しく走っていても「証明できない緑」になります。
  所要時間は `time` の実出力から数えます。SKIP はテストごとの結果を出す詳細な出力から数えます。結果をキャッシュから返した単位は走っていません。
  **SKIP の件数が示すのは「省略されたテストが無い」ことだけです。期待した環境（DB など）で走った根拠にはなりません。**
  テストの補助によっては、必要な資源（DB の接続先など）が無いときに省略しません。代わりの実装（組み込みの DB など）へ**黙って切り替わります**。
  その場合は SKIP 0 件のまま PASS します。「資源を渡し忘れた」のか「代わりの実装で走らせた」のかを出力から区別できません。
  資源を必須にする指定（「この実行は DB 必須」と明示する設定）があれば付けて実行してください。付ければ資源が無いときは SKIP として件数に出ます。
  期待した環境で走ったことは、それを直接示す出力（選ばれた実装の表示・その環境でしか通らないテストが通った行・
  実際に作られた資源の数）で示し、報告に添えます。
  並走本数は `ps -eo pid,etime,command | grep '<テストの命令>' | grep -v grep` の**一覧を目で見て**数えます
  （`grep -c` はラッパのシェルの命令文にも当たります。実測で 3 を返し、実体は 0 でした）。
  **所要時間だけでは偽の緑を見分けられません。** 実例: 並走を `ps` で見ていたときに、3 分以内に終わった全体実行を
  「重いパッケージが走っていないのでは」と疑いました。取り直した結果は正しい緑でした。全体実行はパッケージを並列に実行するので、
  単独で 100 秒かかるパッケージがあっても全体が 3 分で終わるのは矛盾しません。**キャッシュの有無と SKIP 件数までそろって初めて根拠になります。**
  同じ回には**所要時間と SKIP 件数を添えなかったせいで、正しく走っていた検査が「証明できない」まま残った**こともありました。
- **並行実行で失敗したテストは、時間切れに見えなくても競合が原因のことがあります。** 外部のコマンドを子プロセスで呼ぶテストでは
  負荷が高いとその呼び出しが失敗します。実装が fail-open だと**期待した文字列が出ないという「内容の失敗」に見えてしまいます**
  （実例: 全テストを並行で流すと失敗しました。同じテストを単独でキャッシュを使わずに実行すると通りました）。
  **赤を見たら、まずその単位だけを単独でキャッシュを使わずに実行し直します。負荷によるものか本物かを切り分けてください。**
- **文面を検査するテストが失敗したら、期待値より先に「言語が固定されているか」を疑ってください。** 直す順序は次のとおりです。
  ① テストの環境で言語を固定する（子プロセスには言語を指定する環境変数を渡す。HTTP の要求には `Accept-Language` を付ける）→
  ② それでも失敗するなら実装を直す → ③ 期待値を書き換えるのは仕様として文面そのものを変えたときだけ。
  **期待値を別の言語に書き換えて緑にしてはいけません。** 実例: 「クライアントはサーバに言語を伝えない」という
  当時の前提で**複数のテストファイルの期待値が英語に書き換えられました**。その前提は同じ日に別のセッションが覆し（送るようになった）
  期待値は日本語に戻されました。**順序が逆だったら「テストは緑のまま、日本語の利用者には英語が出る」状態が残っていました**。失敗しないまま静かに悪くなる類のものです。
- **これは個人のミスではなく構造的な失敗です**: 送る側（クライアント）と受け取る側（サーバのテスト）を別のセッションが受け持つと
  **片方の前提だけで期待値が書き換わります**。自分の担当範囲の中では筋が通って見えるので、その場では誤りに見えません。
  **言語の受け渡しを作ったら送る側と受け取る側の両方を grep で数えてください**（例: `grep -rn "Accept-Language" <ソースのディレクトリ>`）。
  **送る側が 0 件なら受け取る側はいつも既定の言語を選んでいます**。
- **区切り文字で欄を数えるときは末尾の欄が空になる行を必ずテストに入れます。** `git for-each-ref` の `%(upstream:track)` は
  リモートと完全に同期しているときだけ空になります。しかも**いちばん最後の行では行末の空白として削られます**。
  そのため欄の数で弾く実装はブランチの並び順しだいで判定を黙って落とします（実際に踏みました。テストが先に捕まえました）。
- **push の前に確かめるのは自分の変更の範囲ではなく基点の緑です。** 既定は全検査です。軽い検査だけで押してよいのは
  基点の SHA に全検査が緑だった記録があるときだけです（記録が無ければ全検査を実行します）。**影響範囲が狭いことは基点が緑である根拠になりません**（実例: 文書だけの push が赤い基点を 1 つ先に進めました）。
- **集計（FAIL 0・SKIP 0）が緑でも、目当てのテストが走った根拠にはなりません**。名前での絞り込みの空振り・ビルドの条件・対象の取りこぼしがあると走っていないのに緑に見えます。
  特定の赤の解消や特定の修正を根拠にするときは、キャッシュを使わず詳細な出力で実行します。そのテストが始まった行と通った行を引用してください。
  **名前で絞ったときは、走ったテストの名前を詳細な出力で確かめます**。絞ったつもりのテストがパターンに一致せず
  未実行のまま緑に見えたことがありました。PASS の件数だけでは走っていないテストは見えません。
  **「一致するテストが 0 件」は緑ではありません。** テストが 1 つも走っていないという警告です。ところが終了コードは 0 のままで
  成功の行も出ます。件数を見ないと緑と読み違えます。
- **「X は起きない」を確かめるテストには、同じテストの中に「検出が起きる」側の対照を置きます。** 対照が無いと経路が死んでいても通ってしまいます。
  対照は、確かめたい現象を実際に通るものにします（置いただけでは足りません）。前提が崩れたときは「前提が崩れている」と分かる失敗の文面にしてください。

### 並行セッション（同じプロジェクト）
- **着手の宣言はサーバの状態で行います。** 「これをやります」と伝える前にまずイシューを In Progress にしてください（`looptrack issue next` か
  `looptrack issue status <ID> "In Progress"`）。**メッセージはその通知にすぎません。** 会話は流れて消えますが状態は残ります。
  宣言だけしてサーバを変えないと、ほかのセッションからは誰も手を付けていないのと同じに見えます。
- **`summary` に「※ … は別のセッションが着手しています」と出ていたらそのイシューは取りません。** 引き取るときは先に一声かけ、
  相手が降りてから着手します。長く経っているものは渡したまま放置されているかもしれません（そのときも先に確かめます）。
- **別のセッションに渡すときは渡す側が状態を Todo に戻して担当を外します。** In Progress のまま渡すと受けた側が着手していなくても
  誰かがやっているように見え続けます。
- **着手前に同じ作業ディレクトリで動いているほかのセッションを確かめます**（セッション一覧のツールがあればそれで。無ければ利用者に聞く）。
  ファイルの更新時刻で「相手が終わったか」を判断しないでください。更新時刻は遅れて動く指標です。
- **共有の作業ツリーでは触ったパスだけを stage します**。`git add -A` / `git add .` / `git commit -a` はほかのセッションの未コミットの変更を巻き込みます。
  `git add <パス>` と `git add -u` を使ってください。ペア: PreToolUse `pre-tool-git-guard` はこれらの巻き込み（unstage・amend で戻せる）を
  `ask` で確認します。取り返しのつかないもの（`push --force`・`+` の refspec（`push origin +main`）・`reset --hard`・`clean -f…`・**`switch --discard-changes` / `switch --force`**・
  **パス指定の `checkout` / `restore`**・**他の作業ツリーを指す `-C` / `--work-tree` / `--git-dir` の書き込み**）は **`deny` で止めます**
  （**bypass permissions モードでは `ask` が確認されずに通ると実測で分かったため**）。通す必要があれば利用者に確かめて
  `LOOPTRACK_LOOP_GIT_GUARD_ALLOW` で例外にします。**hook が捕まえるのはうっかりミスだけです**。入れ子のシェル・`eval`・`sudo` などの前置はほどいて判定します。ただし
  コマンド置換・行継続・引用符の無い `C:\…\git.exe`・一覧に無いラッパは確認されずに通ります（このファイルの末尾の「git ガードが止めるもの・止めないもの」）。
- **AI が自分から確認して止まったことを hook が止めたことと取り違えないでください。** AI は危ない操作の前に自分から利用者に可否を
  尋ねて止まることがあります。そのときツール呼び出しはまだ試みられておらず hook は発火していません。「AI が止まった」は「hook が止めた」ではありません。
  ガードが効くかを確かめるときは hook の応答（`deny` の理由の文面）と操作の結果（対象が変わっていないこと）の実出力で判定します。
- **ほかのセッションの作業ツリーを `checkout` / `restore` / `reset --hard` で戻してはいけません。パス指定の `checkout` でも相手の未コミットの変更は復元できません**（実際に失われました）。
- **scratchpad はセッションごとに分かれていますが、1 つのセッションの親と全サブエージェントでは共有されます**（サブエージェントに
  自分の scratchpad のパスを報告させると、親と同じパスを返します）。計測用のファイルにはエージェント固有の接尾辞を付けて衝突しない
  名前にしてください。結果が空や想定外ならまず計測が壊れたことを疑います。実際に並行させたサブエージェントが親の計測スクリプトを黙って
  上書きし、空の結果が「穴が無い」と読まれかけました。
- **引き継ぎは全セッションで同じ 1 ファイルです。自分が書いた節には hook が示す印の行
  （`<!-- looptrack:session <セッション ID> -->`）をそのまま 1 行入れてください。** 印が無いとほかのセッションが書いただけで
  自分の申し送りが「更新済み」に畳まれて書かれないまま黙って終わります。実物の行は作業の完了を検知したときと
  やり直しを求めるときに hook がそのまま出します（セッション ID を自分で調べる必要はありません）。
  印が 1 つも無いファイルはこれまでどおり更新時刻で判定します（`LOOPTRACK_LOOP_HANDOFF_WRITER=mtime` で時刻だけに固定できます）。
- **並行セッションがいる間は、引き継ぎを直接編集せず `looptrack handoff append` で追記します**。読んでから全文を書き戻すと
  その間にほかのセッションが書いた節を消してしまいます。**1 セッションに戻って印をやめるときは `looptrack handoff compact --drop-marks`** を使います
  （印のあるファイルでは自分の印の無い更新は鮮度ガードがやり直しを求めます）。
- **1 タスクの完了はセッションの終了ではありません**。「停止中」と「終了」を同じものとして扱わないでください。
- **競合を検知したらその場で止めて利用者に報告します**。検知した後で書き込みを続けてはいけません。

### サブエージェント（委譲が既定。親のコンテキストは判断に使う）
- **親のコンテキストは「判断」に使い、手順が決まっている作業は出します。** 好みの問題ではなくセッションの寿命の問題です。
  親が手を動かすほど 1 応答あたりの再送が増え、`session-scope-guard` の警告（既定 25 万トークン / 応答）に早く達します。
  **委譲を前提にしないと 1 セッションの寿命が短すぎて仕事が終わりません。**
  - **出すもの**: 検索・調査・実装・テストの実行・**マージと衝突の解決**・**イシューの起票とコメント**・
    **文書の編集**・記録（引き継ぎ・メモ）の更新。「逐次でしかできない」と思える作業も手順が決まっているなら出せます。
  - **親がやるもの**: 何を誰に割り振るか・受け取った結果の検証・**取り消すかどうかの判断**・利用者との対話。
  - 実例: 5 本の並行作業をサブエージェントに出したのに、その後のマージ 3 回・衝突解決 3 回・起票 5 件・日英の文書の編集・
    他セッションへの連絡 6 通を親が抱え込み約 1 時間で警告に達しました（どれも出せる作業でした）。
- **サブエージェントへの指示には「報告は N 行以内」を入れます。** 報告そのものが親のコンテキストを使うからです
  （実例: 1 つの報告が 100 行を超えました）。要るのは結論・変更したパス・検証の合否です。読んだ内容の再掲ではありません。
  親が次に判断するのに要るものだけを行数を指定して出させてください。
- **結果を鵜呑みにしないでください。** 受け取った結果は必ず検証してから統合します。
  **ただし検証もサブエージェントに出せます**（作業させたのとは別のエージェントに実行結果の引用つきで確かめさせる）。
  親がやるのは検証されたと認めるかどうかの判断です。
- **子に push まで任せるときは指示文に「全検査の一式を親に見せ、親が認めてから push」と書きます。**
  「全部緑なら push」と書くと報告は押した後に届きます。**検査の数字だけを短く先に**出させてください（全文は押した後でかまいません）。**「緑には数字を添える」は相手が親のときも押す前に守らせます。**
- **並行で走らせるときは作業ツリーを分けます。** 同じ作業ツリーに 2 つ入れないでください
  （実例: 同じ作業ツリーに 2 つ入れて、未コミットの変更が本当に失われました）。作業ツリーごとにブランチを分けて触ったパスだけを stage します。
- **任せるタスクの難しさに応じてモデルを切り替えます。基準は「間違えたときに気づけるか」です。**
  - **軽いモデルでよいもの**: 検査で機械的にはじける作業（マージと衝突の機械的な解決・検査の実行と結果の転記・
    イシューの起票・文書の体裁・記録の更新）。壊れればテストや検査が赤くなるので取りこぼしが後に残りません。
  - **重いモデルを使うもの**: **失敗しないまま静かに悪くなる**作業（訳の質・既存の書き方との一貫性・原因の切り分け・
    何を捨てて何を残すかの判断）。検査は通るので間違いがレビューされないまま残ります。
- **背景で何かを待たせる作業を出すときは上限の規律を指示文にそのまま書き写します**（→ background-process.md の
  「サブエージェントへ出すときに書き写す一文」）。**規律は親にしか注入されないので、要約して伝えると薄まります。**
  指示文に入れるのは 3 つです: 上限（最大回数か締切）を必ず持たせる・**待ち始める前に待機対象の存在を確かめさせる**・
  **報告に「起こした背景プロセスとその停止」を 1 行で書かせる**。親は報告でその 1 行まで確かめてから統合します
  （実際に上限の無い `until` ループが 1 日で 3 本作られました。うち 1 本は待機対象のパスが存在しませんでした）。

## git ガードが止めるもの・止めないもの（注入しない。参照用）

`pre-tool-git-guard` はコマンド文字列を**実際に実行される語**に直してから、`;`・`&`・`|`・かっこ・改行で
分けた**単純コマンドの先頭の語**が `git` かを見ます。直すのは 2 段です。秘密のガード・待ちループのガードと**同じ処理**を呼びます
（規則を 2 か所に写すと次に直すとき片方だけが直るからです）。違うのは**どの位置で入れ子をほどくか**の引数だけです。
リダイレクト（`2>&1`・`2>/dev/null`・`>out.log`・`&>/dev/null`）では単純コマンドは終わりません。演算子に空白を挟まずに付いた
記述子（`2>&1` の `2`）と行き先（`/dev/null`）は語から外して判定します。そのため `git checkout main 2>&1 | tail -20` は
ブランチの切り替えとして通り、`git checkout -- <パス> 2>&1` はこれまでどおり `deny` になります。

1. **入れ子のシェルを 1 段ほどきます**（`bash` / `sh` / `zsh` / `dash` の `-c` と `eval` の引用符。
   `-lc`・`-ec`・`-o pipefail -c` のように短い選択肢がまとまった形も `-c` として読む）。
   **シェルの名前は `.exe` も含めて大小を区別しません**。macOS と Windows のファイルシステムは大小を
   区別しないので `BASH -c 'git clean -fd'`・`BASH.EXE -c '…'` は実際に実行されます（実機で確かめました）。
   **`eval` だけは区別します**。組込みなので `EVAL` は `command not found` になります（実機で確かめました）。
2. **前置の語を落とします**（`sudo`・`doas`・`env`・`xargs`・`nohup`・`time`・`command`・`nice`・`stdbuf`・
   `timeout`・`setsid`・`flock`・`script`）。ほどいた中身の先頭にあるもの（`bash -c 'sudo git …'`）も落とします。

引用符の組を数えるときは打ち消した `'`（`echo don\'t ; bash -c '…'`）と二重引用符の中の `\"` は引用符に数えません。
コマンドの位置でほどくときはコメント（語の先頭の `#` から行末まで）も飛ばします。

**ほどくのは「コマンドの位置」だけです**（git ガードと待ちループのガード。秘密のガードは位置を問いません）。コマンドの位置とは
文字列の先頭と引用符の外の区切りの直後、それに**後ろにコマンドが続くものの直後**のことです。

- 複合コマンドの語: `if`・`then`・`else`・`elif`・`do`・`while`・`until`・`!`・`{`
- 変数の指定: `x=1 bash -c '…'`・`FOO=bar BAZ=1 bash -c '…'`
- 前置の語とその選択肢（実行ファイルのパス付きも）: `sudo bash -c '…'`・`timeout 30 bash -c '…'`・
  `/usr/bin/sudo bash -c '…'`。**前置の語が飲み込むのは選択肢の形（`-x`・`VAR=v`・数）だけ**です。
  値を別の語で取る短い選択肢はその値を 1 語だけ飲み込みます（`env -u FOO bash -c '…'`・`sudo -u deploy bash -c '…'`・
  `xargs -a f bash -c '…'`）。`flock` と `script` はコマンドの前に作業対象を 1 語取ります
  （`flock /tmp/l bash -c '…'`・`script -q /tmp/o bash -c '…'`）。
  **任意の数の語を飲み込ませないのが要点です**。飲み込ませると `timeout 30 ssh host bash -c '…'` の `bash -c` が
  コマンドの位置に見え、**遠隔で実行されるだけの形まで `deny` になります**（実測で 24 形）。
- `find … -exec` / `-execdir` の直後

**引数として渡すだけの語は含めません。** `deny` は bypass permissions でも止まるので何も実行されない形まで
止めるとこのガードについて書く作業そのものが止まってしまいます。そのため次は**実測で通ります**:
`echo bash -c 'git reset --hard'`・`ls -l bash -c '…'`・`printf '%s' bash -c '…'`・
`rg -n "bash -c 'git reset --hard'" docs/`・`git commit -m "bash -c 'git reset --hard' は止まる"`・
**前置の語を挟んだ形**（`timeout 30 ssh host bash -c '…'`・`nohup ssh host bash -c '…'`・
`env DOCKER_HOST=x docker run img bash -c '…'`・`sudo echo bash -c '…'`・`sudo ls -l bash -c '…'`）。

**実測で `deny` になる形**: `git push origin +main`・`sudo git push origin +HEAD:main`・`sudo git reset --hard`・`xargs git reset --hard`・`env git clean -fd`・
`setsid git reset --hard`・`bash -c 'git reset --hard'`・`eval "git clean -fd"`・`BASH -c 'git reset --hard'`・
`BASH.EXE -c '…'`・`/usr/bin/sudo bash -c '…'`・`sudo bash -c '…'`・`x=1 bash -c '…'`・
`if bash -c 'git reset --hard'; then …`・`find . -exec bash -c 'git clean -fd' \;`・`echo don\'t ; bash -c 'git reset --hard'`・
`case a in a) git clean -fd;; esac`（`)` は区切りなのでこの 1 つは入れ子が無くても止まります）。

### 止めないもの（設計として塞がない・塞げないと決めたもの。どれも実測）

- **複合コマンドの語の後ろに `git` が直接来る形**: `if true; then git reset --hard; fi`・`{ git reset --hard; }`・
  `! git push --force origin main`・`x=1 git reset --hard`・`find . -exec git clean -fd \;`・
  `for f in a; do git clean -fd; done`・`while git reset --hard; do :; done`。
  **「コマンドの位置」が効くのはほどく段だけで、単純コマンドの先頭の語を見る本体には効きません**
  （先頭の語が `then`・`x=1` などになります）。**基点でも通ります**。この回で新しく開いた穴ではありません。
- **一覧に無いラッパ + 入れ子のシェル**: `caffeinate bash -c 'git reset --hard'`。前置の語の一覧にも
  複合コマンドの語にも無いのでコマンドの位置になりません（**基点でも通ります**）。
- **値を別の語で取る選択肢を挟む前置 + 直接の `git`**: `env -u FOO git reset --hard`・
  `sudo -u deploy git clean -fd`・`flock /tmp/l git clean -fd`。前置の語として読み切れず
  残った値の語が先頭になります（**基点でも通ります**）。
- **入れ子のシェルがコマンドの位置に無い形**（上の「引数として渡すだけの語」）。通すと決めたのは 2 種類です。
  **(i) 引数の位置にあって何も実行されない形**と**(ii) 手元ではない場所で実行される形**（`ssh`・`docker run`・
  `docker exec`・`kubectl exec`）です。**git ガードだけ**の扱いです。
  **秘密のガードは位置を問わないのでこれらも確認します**（`ask` なら人がその場で通せるため）。
- **任意の処理系から git を呼ぶ形**（`ruby -e '...'` の中から）・**変数でコマンド名を組む形**（`G=git; $G reset --hard`）・
  **エイリアスと関数**（`alias gr='git reset --hard'; gr`）。展開した後の文字列は hook には届きません。
- **2 段以上の入れ子のシェル**（`bash -c "bash -c 'git reset --hard'"`）。ほどくのは 1 段だけという設計どおりです。
- **`c` が最後でない結合形**（`bash -cx 'git reset --hard'`・`-cl`・`-ce`）。実際のシェルでは実行されますが
  `-c` を短い選択肢の並びの**最後**として読む作りなので当たりません（**基点でも通ります**）。
- **ANSI-C の引用で渡す形**（`bash -c $'git reset --hard'`）・**パイプでシェルに流す形**
  （`echo 'git reset --hard' | bash`・`| sh`・`| bash -s`）。
- **コマンド置換**（`echo "$(git reset --hard)"`・バッククォート）と**行末の継続**
  （`git reset --hard` + バックスラッシュ + 改行）。
- **コメントの中の引用符の後ろ**（`git status # don't` + 改行 + `bash -c 'git reset --hard'`）。ほどく段はコメントを
  飛ばします。ところが単純コマンドに分ける段はコメントの中の `'` を開きと数えます。そのため後ろの行を引用符の中と取り違えます。
- **引用符で囲まない Windows の絶対パス**（`C:\git\git.exe clean -fd`）。語に分けるときにバックスラッシュが
  打ち消しとして消えて、コマンド名が `git.exe` と一致しなくなります。引用符で囲めば止まります。
- **`git` を経由しない破壊**（`rm -rf .git`・`find … -delete`）。**git ガードは git のコマンドを見る hook です**。
  任意の削除はこの hook の対象ではありません（別の問題として扱います）。

hook が捕まえるのはうっかりミスだけで規律の代わりにはなりません。
