# 実装イテレーションの手順（/iterate）

> 規律の元の定義は rules の `iteration-discipline.md` にあります。この文書には操作の手順だけを書きます。
> プロジェクト側の rules に固有の実装規律（ワークフロー・テスト階層・コミット規約）があれば、それに従ってください。
> イシューの操作全般は skill `/issue` を見てください。

## 0. 前提の確認（毎イテレーションの冒頭）

```bash
looptrack issue list --type bug     # 未解決の bug を見る（「該当なし」= 0 件）
looptrack issue next --dry-run      # 次に着手するイシュー（確かめるだけ）
```

- **bug を抱えたまま新しい実装を積み上げません**。直せるものは先に直します（§3 の復帰ループ）。判断に迷うものは利用者に諮ってください。

## 1. 着手

```bash
looptrack issue next                # 自分が着手中のもの、無ければ着手可能な最上位を In Progress に
```

- 実装の前に、必ず対象の要件と設計を読みます。設計と食い違う判断が要るときは推測で実装せず、起票して利用者に諮ります。
- 実装の途中で決めたこと（許容範囲の中の判断）は、イシューのコメントに残してください。

## 2. 実装 → ゲート

実装し、テストは**受け入れ条件から**書きます（受け入れ条件の項目をテスト名やアサーションにする）。そのあと次を実行します:

```bash
looptrack gates               # 段は LOOPTRACK_LOOP_GATES_STAGES（既定 build lint test）。fail-fast
```

## 3. 失敗したら（復帰ループ）

1. **問題 1 件につき bug 1 件を、その場で起票します**。まとめないでください。本文は再現 / 期待 = 要件・設計の該当箇所 / 実際 = 実ログの引用 / 検出した段階 です:

   ```bash
   looptrack issue new "<症状の 1 行>" --type bug --priority P1 --traces <要件のイシュー> --body "$(cat <<'EOF'
   再現: …
   期待: …（要件・設計の該当箇所）
   実際: …（実ログの引用）
   検出した段階: …
   EOF
   )"
   ```

2. bug を In Progress にして直します。
3. **同じ問題を検出するテストを足してから**、`gates.sh` をもう一度実行します。
4. 全緑になったら、実出力を引用して bug を close します。この周で見つけた問題が片付くまで 1〜4 を繰り返します。

## 4. 完了（close の条件）

次をすべて満たしてから close します:

- `gates.sh` が全段グリーン（「═══ gates 結果 ═══」のブロックをそのままコメントに引用）
- この周で見つけた問題がすべて起票済みで、直したものは close 済み
- 受け入れ条件ごとの合否（自動テストにできなかったものは「何を・どう確かめたか」）

```bash
looptrack issue close <ID> --comment "<gates 結果の引用 + 受け入れ条件ごとの合否>"
```

- そのあとコミットし（イシュー単位。触ったパスだけを stage）、引き継ぎを更新します（skill `session-handoff`）。

## 5. 次へ（自動進行）

- §0 に戻り、利用者に 1 つずつ確かめずに次のイシューへ進んでかまいません。
- **止めて利用者に諮るのは次のときです**: 親イシューの範囲を超える / 設計の変更が要る / 要件の解釈が割れる /
  同じ bug の修正が 3 回失敗した（やり方を考え直す必要がある）。
