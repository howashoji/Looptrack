# トークンレポート作成（token-report）

イシュー管理サーバに貯まったトークン消費の集計から期間のレポートを PDF で作ります。
**数値はサーバの集計をそのまま使い、AI は本文（考察・提案）だけを書きます。** PDF は手元に保存してサーバには置きません。
作ったら台帳に 1 行登録します。次回の「前回以降」の起点になります。画面からの依頼ならその依頼が完了になります。

設計: Looptrack の `docs/server/DESIGN.md` §5-4「レポートの集計と台帳」「レポートの作成依頼」。

## 前提

- `looptrack issue config` でサーバとプロジェクトが出ること（トークンが未登録なら先に login）
- 台帳への登録は editor 以上（閲覧者は集計まで）
- PDF は `looptrack report pdf` で作ります（`looptrack version` が通るか確かめてください）。別の処理系も PDF ライブラリも要りません。
  日本語フォントは `TOKEN_REPORT_FONT`（TrueType のパス）→ 実行ファイルに埋め込んだ BIZ UDGothic → 手元の既定の置き場の順に探します。
  扱えるのは TrueType（.ttf・TTC）だけです（CFF の .otf は使えません）

以下では `IM="looptrack issue"` とします（別の AI では読み替えてください）。

## 手順

### 0. 何を作るか決める（最初に行う）

| 指示 | 集計の指定 |
| -- | -- |
| 「トークンレポートを作成して（依頼 #N）」・要約に依頼が出ている | `--request N`（期間・対象・メモは依頼に入っている） |
| 「前回以降の…」・期間の指定なし | `--since-last`（台帳の最新のデータ終端から今まで） |
| 「9 月分の…」など期間の指定あり | `--from 2026-09-01 --to 2026-09-30`（日付だけの `--to` はその日を含む・プロジェクトの現地時刻。既定は日本時間） |

未完了の依頼の一覧は `$IM usage requests` で見られます。依頼が複数あるときは古い順に 1 件ずつ作ってください（まとめません）。
期間の指定も依頼も無いときは `--since-last` で進めてかまいません。台帳の状況は `$IM usage ledger list` で見られます。

### 1. 集計を取る（判断なし）

```bash
OUT="${TOKEN_REPORT_DIR:-$HOME/Documents/トークンレポート}/<プロジェクトの slug>"   # slug は $IM config で分かる
mkdir -p "$OUT"; STAMP=$(date +%Y%m%d)
$IM usage report --request N --json > "$OUT/トークンレポート_$STAMP.集計.json"   # または --since-last / --from … --to …
$IM usage report --request N                                                   # 同じ集計を表で読む
```

- `total_tokens` が 0（区間 0）なら PDF を作らずに利用者に報告して止めます（前回のレポートの直後など）。依頼の場合はその旨を利用者に伝えて判断を仰ぎます
- `excluded_conversations`（レポート対象外の会話）と `inconsistent`（累計が減った区間）には本文の「データの限界」で触れます
- 案件別（`by_case`）は区間ごとに案件を 1 つ決めた集計です。帰属先イシューのラベルから（無ければブランチ名から）案件（例 `CASE-101`。形はプロジェクト別ルール `usage.case_pattern`）を決めます。
  合計は全体と一致します（`by_label` は複数ラベルのイシューをそれぞれに数えるので一致しません）。正規表現はプロジェクト別ルールの
  `usage.case_pattern` です（`case_pattern` に出ます）。空なら未設定で全部「（なし）」になります。案件別だけを読むなら `usage report … --json` の `by_case` を使います。
  表なら API の `group=label`（MCP の `usage_report` なら `group: "label"`）を使います
- 依頼の `target`（対象）が「ラベル api」などのときも集計はプロジェクト全体で取ります（サーバは対象で絞りません）。
  本文でその対象に焦点を当て、数表（イシュー別・案件別・ラベル別）で該当する行を示してください

### 2. 材料を読む（判断）

- 上位のイシュー: `$IM show <ID>`（何をした作業か）・`$IM usage show <ID>`（段階ごとの消費）
- 期間の git の履歴（プロジェクトのリポジトリ）: `git log --since=<from> --until=<to> --oneline`
- 依頼のメモ（`request.note`）に指示があればそれに従います

### 3. 本文 JSON を書く（判断）

`$OUT/トークンレポート_$STAMP.本文.json` に書きます。数表は `looptrack report pdf` が集計 JSON から作るので**本文に数表を手で写さないでください**。
本文の中で数値を引くときは集計 JSON の値をそのまま使います。

```json
{
  "title": "トークンレポート 2026年9月（<プロジェクト名>）",
  "subtitle": "<プロジェクト名>・<依頼 #N / 前回以降 / 期間指定>",
  "author": "作成: <AI 名>（<日付>）",
  "sections": [
    {"heading": "1. 全体サマリー", "paragraphs": ["…"], "bullets": ["…"]},
    {"auto": "summary"},
    {"auto": "by_issue", "limit": 15},
    {"auto": "by_case"}, {"auto": "by_label"}, {"auto": "by_type"}, {"auto": "by_stage"}, {"auto": "by_client"},
    {"auto": "conversations", "limit": 20},
    {"heading": "2. 作業の内訳", "paragraphs": ["…"]},
    {"heading": "3. 関与と AI の挙動への影響", "table": {"columns": ["観点", "好影響", "悪影響", "実測"], "rows": [["…", "…", "…", "…"]]}},
    {"heading": "4. トークン効率を高める提案", "bullets": ["…"]},
    {"heading": "5. データの限界", "paragraphs": ["…"], "note": "…"}
  ]
}
```

- 章: `heading`（必須）と `paragraphs`（段落の配列）・`bullets`（箇条書き）・`table`・`note`（小さい注記）で書きます。
  表は `columns` と同じ列数の `rows` を持ちます。数値の列を右寄せにするなら `"numeric": [列番号…]`（右寄せの列は折り返さない）。
  ID・状態など折り返させたくない文字の列は `"nowrap": [列番号…]`（列番号は 0 始まり）。表の下の注記は `"notes": […]` です
- 数表: `{"auto": "<名前>"}` の位置に入ります。名前は `summary`（合計・未帰属・対象外）・`by_issue`・`by_case`（案件別）・`by_label`・`by_type`・`by_stage`・
  `by_client`・`conversations` です。`limit` で上位 N 件に絞れます（既定は by_issue・conversations が 20）。`heading` で見出しを変えられます。
  `auto` を 1 つも書かなければ最初の章の後に全部入ります
- 見出しに「データの限界」を含む章が無いと `looptrack report pdf` は止まります（下の執筆ルール）

章立ての目安: 1 全体サマリー（合計・内訳・イシュー数・会話数）→ 数表 → 2 作業の内訳（上位のイシューが何の作業だったか）→
3 関与と AI の挙動への影響（好影響・悪影響の両面）→ 4 提案（実測の根拠つき）→ 5 データの限界。

### 4. PDF を作る（looptrack report pdf）

```bash
looptrack report pdf --report "$OUT/トークンレポート_$STAMP.集計.json" \
  --content "$OUT/トークンレポート_$STAMP.本文.json" --check          # 先に検査（章・表の数と合計）
looptrack report pdf --report "$OUT/トークンレポート_$STAMP.集計.json" \
  --content "$OUT/トークンレポート_$STAMP.本文.json" --out "$OUT/トークンレポート_$STAMP.pdf"
```

- 保存先は `$TOKEN_REPORT_DIR` です（既定は `~/Documents/トークンレポート/<slug>/`）。**リポジトリの中には置かないでください**。本文に顧客名や
  未修正の脆弱性が混ざることがあるからです。利用者が別の場所を指定したらそれに従います
- 集計 JSON と本文 JSON も再生成できるよう PDF の横に残します。改訂は新しい日付で作って旧版は残します
- 作った PDF を開いて表と本文が崩れていないか確かめます（Read で PDF を読めるなら 1〜2 ページ）

### 5. 台帳に登録する（必須・最後に行う・取り消せない）

```bash
$IM usage ledger add "<レポート名>" --from-report "$OUT/トークンレポート_$STAMP.集計.json" --note "トークンレポート_$STAMP.pdf"
```

- `--from-report` は集計したときの期間・データ終端・除外した会話・合計をそのまま登録します。**`--request N` で集計したときは依頼の番号も自動で付いて依頼が完了になります**
  （別の方法で集計したのに依頼に応えたなら `--request-id N` を足してください）
- レポート名はプロジェクトの中で一意にします（例: `2026年9月`・`2026-09-18 依頼#3`）。同じ名前は 409 になります
- 登録しないと次回の「前回以降」の起点が進まず期間が重なります。PDF を作れなかったときは登録しません
- MCP しか使えない AI は `usage_report`（`request_id`・`format: json`）→ `add_usage_ledger`（`request_id` を付ける）の順に使います

### 6. 報告

利用者には次を返します: PDF の保存先・対象期間とデータ終端・合計トークン・台帳の番号（`#N`）・依頼の番号（あれば「完了」）・
データの限界の要点。イシューに関係する作業ならそのイシューにもコメントで記録してください。

## 執筆ルール（厳守）

- **事実に基づいて書きます**。「人間の関与が不可欠」のような主張を題名や結論にしないでください。数値と観測した事実を示します。解釈は
  「関与のタイミングと粒度が差を生んだ」くらいにとどめます
- 好影響と悪影響の**両面**を整理します（片方だけの構成にはしません）
- すべての主張に実測値（トークン・件数・区間・分）を添えます。数値は集計 JSON の値を使います。手で丸めた値を混ぜないでください
- 「データの限界」を必ず設けます。最低限次を書きます:
  - トークンは会話記録の累計の差分。イシューへの帰属は「その時点で作業中のイシュー」で決まる（並行作業は分けられない）
  - 未帰属（クローズ後のターン終了など）とレポート対象外にした会話は合計に入れていない
  - 送信が遅れて前回のデータ終端より前の時刻で届いたスナップショットはどのレポートにも入らない
  - キャッシュ読取は割安に課金されるのでトークン数は費用に比例しない（金額換算はしていない）
  - 累計が減った区間（不整合）があればその件数
- 顧客名・未修正の脆弱性の詳細・認証情報は本文に書きません。イシューのタイトルは数表に出ます。出してよいかを依頼のメモか利用者の指示で確かめてください
- 指示文（人間の発話）は既定ではサーバに送られていません。本文で引用しないでください
