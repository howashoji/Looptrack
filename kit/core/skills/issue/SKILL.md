# 課題管理スキル（イシュー管理サーバ）

CLI は `looptrack issue` です（API モード）。サーバとプロジェクトは `.claude/settings.json` の `env` にある `LOOPTRACK_API_URL` / `LOOPTRACK_PROJECT` で
決まります。**ローカルにイシューのファイルはありません**。

**最初に `looptrack issue guide` を読んでください**。共通規則・このプロジェクトのルール・運用文書を 1 回で返します（MCP なら `guide` ツール）。
型・ラベル・`--refs` の使い方・プロジェクト別ルールといった**プロジェクト固有の決まりは、すべて guide にあります**（この skill には書きません）。

## いつ使うか

- 作業の依頼を受けたとき（**作業はイシューから始めます**。会話だけで進めません）
- 調査中に別の課題・未決事項・不具合を見つけたとき（**その場で起票します。先送りしません**）
- 作業の状態が変わったとき（着手 / 完了）
- 次に何をやるか決めるとき

## 0. 接続を確かめる（エラーが出たとき）

```bash
looptrack issue config   # モード・サーバ・プロジェクト・自分の権限・トークンの取得元・導入セット
```

`アクセストークンがありません` / `トークンが無効です` / `失効しているか期限切れです` / `ログインの有効期限が切れました` が出たら、
利用者の承認を得て `looptrack issue login --browser --url <サーバの URL>` を実行します。開いたブラウザで
**利用者に**ログインと承認をしてもらってください。待ち受けは最長 5 分です。トークンは会話に出ず、AI はトークンを扱いません。
ブラウザの無い環境では、利用者にトークンの発行（サーバの `/account`）と `login --url <サーバの URL>` への貼り付けを頼みます。
`config` がサーバを示せずにエラーで終わったら（`LOOPTRACK_API_URL` が無いというエラー）、`env` がこのプロセスに渡っていません。
`.claude/settings.json` の `env` は Claude Code のセッションにしか渡らないので、利用者のターミナルで打つときは
`LOOPTRACK_API_URL=… LOOPTRACK_PROJECT=…` を前に付けてください。

## 1. ループの 1 周

```bash
looptrack issue next              # 着手（自分が着手中のものか、着手可能な最上位を In Progress に）。確かめるだけなら --dry-run
looptrack issue comment <ID> "$(cat <<'EOF'
原因・判断・方針（分かった時点で）
EOF
)"
looptrack issue close <ID> --comment "受け入れ条件の検証結果"
looptrack issue next              # 次の周
```

- **原因や判断は、分かった時点でコメントします**。結論だけを後からまとめないでください。コメントは append-only です
- **受け入れ条件の検証結果をコメントに残してから閉じます**。検証しないまま閉じてはいけません
- 状態だけを変えるときは `status <ID> "<状態>" --comment "…"` を使います

### 人の判断待ち

- 利用者の判断が要るもの（仕様の解釈・見た目・方針の選択・確かめてほしいもの）は Done にしません。
  `status <ID> "In Review" --comment "判断してほしい点: …"` にします
- In Review があれば、**次の `next` の前に**利用者に示します（何を作ったか・検証結果・判断してほしい点）。
  返答はコメントの先頭に `判断:`（了承・指示）か `差し戻し:`（やり直しと方針）を付けて残します。`判断:` なら
  `close <ID> --comment "判断: …"`、`差し戻し:` なら `status <ID> Todo --comment "差し戻し: …"` です
- 利用者がいない・答えが無いときは、In Review のまま次の `next` に進みます（催促はしません）。一覧は `list --status "In Review"` で見られます

### 外からの反応

- 参加者・テスター・利用者の反応（感想・不具合の報告・要望）を利用者から聞いたら、該当するイシューに
  先頭を `フィードバック:` にしてコメントします（`フィードバック: 〈誰から・いつ・どの場面で〉 〈内容〉`。該当が無ければ起票してから）
- まだ応答していないフィードバックは、次の `next` の前に利用者に示して対応（方針のコメント・起票・状態変更）を決めます。
  応答は先頭語の無いコメントで残します

## 2. 起票する

```bash
looptrack issue new "タイトル" --type task --traces <要件ID> --body "$(cat <<'EOF'
何をするか・なぜか（「内容」節に入る）

## 受け入れ条件

- [ ] テスト可能な形で書く
EOF
)"
```

- `--type`: requirement / design / task / bug / test / epic。**design / task / test / bug には `--traces <要件イシューID>` を付けます**
- `--traces` はイシュー ID 専用です。文書 ID やラベルの決まりはプロジェクトごとに違います（guide を見てください）
- 待ちがあるなら `--blocked-by <ID>` を付けます。コメントに書くだけでは、着手できるかどうかの判定に効きません
- 本文やコメントをシェル経由で渡すときは、クォート付きのヒアドキュメント（`<<'EOF'`）で囲みます

## 3. 本文を直す

```bash
looptrack issue edit <ID>   # → .claude/.looptrack-work/<ID>.md（版番号つき作業コピー）を Read / Edit で直す
looptrack issue push <ID>   # 反映。競合したら差分を取り込んで push --rebase
```

コメント節は編集できません（追記は `comment` で）。クローズ済みの本文も直せません（蒸し返すなら新規に起票して参照します）。

## 4. 探す・全体を見る

```bash
looptrack issue summary                 # いまの周・人の判断待ち・外からの反応（セッション開始の hook と同じ）
looptrack issue ready                   # blocked_by が全て解決済みのもの
looptrack issue list --status "In Progress"
looptrack issue list --type bug         # 「該当なし」= 未解決 bug 0 件
looptrack issue show <ID>
looptrack issue matrix                  # 要件 → 設計 / 実装 / テストの対応と警告
```

閲覧画面はサーバの `/p/<プロジェクト>/` です（ログイン必須・**閲覧専用**）。状態の変更やコメントは必ず `looptrack issue` で行ってください。

## 拒否されたとき

採番・append-only・クローズ済みの不変・プロジェクト別ルールはサーバが強制します。拒否されたら、**メッセージにある「次に打つコマンド」に従ってください**。
ルールを外す正当な理由（利用者のはっきりした指示など）があるときだけ `--override "<理由>"` を使います（理由はサーバに記録されます）。

## やってはいけないこと

- **イシューを立てずに作業を始める**（経緯が残らず、利用者が後から追えません）
- **「更新します」「起票します」と書いて、そのターンで実行しない**（参照したイシューを更新しないまま終えると、鮮度ガードがやり直しを求めます）
- **待ちをコメントだけに書く**（`blocked_by` に入れないと、着手できるかどうかの判定が働きません）
- **受け入れ条件を検証せずに Done にする**
- **クローズ済みイシューを編集する**（サーバが拒否します。蒸し返すなら新規イシューを立てて参照します）
- **サーバに拒否された操作を別の経路で回避する**（MCP や edit で状態を書き換えるなど）
- **アクセストークンを会話・コミット・イシューに書く**
- **引き継ぎの記憶（memory・handoff）の内容をイシューに書く**（役割が違います）
