### このシステムで何が整うか（ループエンジニアリングの基盤）

イシューを中心に「起票 → 着手（next）→ 作業 → 検証 → クローズ → 次へ」を AI が回します。規則（採番・append-only・クローズ済み不変・プロジェクト別ルール）はサーバが強制し、各段階のトークン消費は記録されます。入れ子の 3 つのループで言うと次のとおりです:

- **① AI の作業ループ（数分）**: AI が上の 1 周を自走する。イシューに「## 検証コマンド」を書くと、`verify` が手元で実行して結果をイシューに残し、閉じる前に機械が判定する（プロジェクトによっては成功していないと閉じられない）。
- **② 人の判断のループ（数十分〜数時間）**: 人の判断が要るものは In Review に集まり、`summary` に滞留（48 時間超に印）が出る。AI は次の `next` の前に判断を持ちかけ（prompt `review`）、返答を `判断:` / `差し戻し:` で残して動かす。人は判断だけをする。
- **③ 外からの反応のループ（数時間〜数週）**: 利用者・テスターから聞いた反応を AI が `フィードバック:` 付きのコメントでイシューに戻し、`summary` の「外からの反応」に未応答が並ぶ。応答（方針のコメント・起票・状態変更）で消える。

導入のされ方によって効き方が変わります:

- **core だけ（最小ループ）**: セッションの冒頭に 3 層の要約（いまの周・人の判断待ち・外からの反応）が注入されます。`next` で着手し、参照したイシューを更新せずに終えようとするとやり直しを求められます。消費は段階別に貯まります。
- **loop を足すと**: 「確認して」と頼まれたときは編集が止まり、ツール呼び出しの書式ミスにはやり直しが求められます。作業が終わるたびに引き継ぎ記憶の更新が求められ、文脈の大きさと放置された背景プロセスも見張られます。別のリポジトリ・プロジェクトへの変更は利用者に確認されます。逸脱の検知は hook に任せ、人は判断に集中できます。loop を入れるかどうかは利用者が決めます（AI が勝手に入れてはいけません）。

### 前提

イシューの元データはサーバ（DB）にあります。手元にファイルは無く、git の操作も要りません。操作は CLI（`looptrack issue <サブコマンド>`）か MCP のツールで行い、どちらも同じ規則で検証されます。CLI は `looptrack` の実行ファイル 1 つで動きます（別の処理系は要りません）。

### 作業の進め方（ループの 1 周）

1. **着手**: `looptrack issue next`（MCP は `next`）。自分が着手中のイシューがあればそれを、無ければ着手可能な最上位を In Progress にして、本文・受け入れ条件・関連を返します。epic のように未クローズの子を持つ束ねは、In Progress でも着手中として扱わず、その子から選びます。`--type`（MCP は `types`）は着手中のものの選び方にも効きます。状態を変えずに確かめるときは `--dry-run`（MCP は `dry_run`）を付けます。
2. **作業**: 原因・判断・方針が分かった時点で `looptrack issue comment <ID> "…"`（MCP は `add_comment`）を実行します。結論だけを後から書かないでください。
3. **検証**: 受け入れ条件を 1 つずつ確かめます。
4. **完了**: `looptrack issue close <ID> --comment "受け入れ条件の検証結果"`（MCP は `set_status` で Done と `comment`）。検証結果を残さずに Done にしてはいけません。
   - **要件の検証と close**: 閉じたイシューが traces で指す要件の下位（その要件を traces で指すイシュー）がこれですべて閉じると、close の応答の末尾に、その要件の検証と close を促す行が要件ごとに 1 行出ます（`looptrack issue show <要件ID>` と close のコマンドを含む）。**文面ではなくこのコマンドで判断してください**（文面は利用者の言語で変わります）。そのまま次の `next` に進まず、要件の受け入れ条件を 1 つずつ確かめます（`looptrack issue show <要件ID>`。MCP は `get_issue`）。満たしていれば `looptrack issue close <要件ID> --comment "受け入れ条件の検証結果"` で閉じます。満たしていなければ足りない分を起票し（`--traces <要件ID>`）、コメントに残します。利用者の判断が要るなら In Review にします。
   - 取りこぼしは、`looptrack issue matrix` の「下位がすべて完了したのに開いている要件」と `summary` の ① に並びます。下位が全部 Canceled の要件は対象外です。作らないと決めただけなので、要件を取り下げる（Canceled）か下位を起票し直すかを利用者と決めます。

**人の判断待ち**: 自分の作業で利用者の判断が要るもの（仕様の解釈・見た目・方針の選択・受け入れ条件を満たしたが確かめてほしいもの）は、Done にせず `looptrack issue status <ID> "In Review" --comment "判断してほしい点: …"` にする。
In Review のイシューがあれば、**次の `next` の前に**利用者に示す: 何を作ったか・検証結果（verify の記録と受け入れ条件ごとの結果）・判断してほしい点。
利用者の返答はコメントの**先頭に `判断:`**（了承・指示）か **`差し戻し:`**（やり直し。方針も書く）を付けて残し、`判断:` なら Done（`close --comment "判断: …"`）、`差し戻し:` なら Todo に戻す（`status <ID> Todo --comment "差し戻し: …"`）。
利用者がいない・答えが無いときは In Review のまま次の `next` へ進む（催促しない。`summary` の「人の判断待ち」に滞留が出る）。

**外からの反応**: 利用者との会話で、参加者・テスター・利用者の反応（使ってみた感想・不具合の報告・要望）を聞いたら、該当するイシューに**先頭 `フィードバック:`** を付けてコメントする（`フィードバック: 〈誰から・いつ・どの場面で〉 〈内容〉`）。該当が無ければ起票してからコメントする。
`summary` の「外からの反応」に未応答のものがあれば、次の `next` の前に利用者に示して対応（方針のコメント・起票・状態変更）を決め、先頭語の無いコメントで応答を残す。

5. 次の周へ進みます（1 に戻る）。着手可能なものが無ければ、`looptrack issue ready` / `summary` で全体を見て利用者に相談してください。

### 起票・編集

- **作業はイシューから始めます。会話だけで進めないでください。** 不具合・別の課題・未決事項は見つけた時点で起票します（`looptrack issue new "タイトル" --type bug …`、MCP は `create_issue`）。
- 型: requirement / design / task / bug / test / epic。状態: Backlog / Todo / In Progress / In Review / Done / Canceled。優先度: P0〜P3。
- 待ちは `--blocked-by <ID>` に入れます。コメントに書くだけでは、着手できるかどうかの判定に効きません。
- `--traces` は**実在するイシュー ID 専用**です（design / task / test / bug は要件のイシューを指します）。文書 ID（FR- / NFR- / UC- / ISS- / DEC-）は `--refs` に入れます。
  blocked_by / traces / refs は 1 要素に ID 1 つです。MCP・API の配列で `"A B"` のように空白で区切ると拒否されます（CLI はカンマでも空白でも区切れます）。
- 受け入れ条件は**テスト可能な形**で書きます（「速い」「使いやすい」のような曖昧な語は使いません）。
- 本文の編集は `looptrack issue edit <ID>` → `.claude/.looptrack-work/<ID>.md` を直す → `looptrack issue push <ID>` の順です（MCP は `get_issue` の version と全文を `update_issue` へ）。競合したら、表示された指示どおりに取り込んでやり直します。
- 本文やコメントをシェル経由で渡すときは、クォート付きのヒアドキュメント（`"$(cat <<'EOF' … EOF)"`）で囲みます。囲まないとバッククォートや `$( )` が実行され、本文が壊れます。

### 担当者（重複作業の防止）

**担当者**: 他の利用者が担当のイシューは In Progress にしない・本文や項目を直さない（サーバが 422 `assigned_to_other` で拒否する）。依頼や確認はコメントで伝える。引き継ぐとき・担当者に代わって直すときは、利用者に確認してから `--override "理由"`（MCP は `override_reason`）を付ける。In Progress にするときの override と `assign <ID> me --override "理由"`（MCP は `assign_issue`）は担当が自分に替わる（引き継ぎ）。本文の編集（`push` / `update_issue`）の override は担当を替えずに通り、誰が理由付きで直したかが記録に残る。`next` は自分が担当か未設定のイシューだけを取る。In Progress 以外への状態変更とコメントは担当に関係なくできる。

### 変えられないもの・やってはいけないこと

- コメントは追記だけです。クローズ済み（Done / Canceled）の本文・項目は編集できません（蒸し返すなら新規に起票して本文で参照します）。
- プロジェクト別ルールで拒否されたら、**メッセージに書かれた次の行動**をとってください。別の経路（MCP・edit など）で回避してはいけません。上書き（`--override "理由"`）は、利用者のはっきりした指示があるときだけ使います。
- アクセストークンを会話・コミット・イシュー・ログに書かないでください。ログインは `looptrack issue login --browser` で行います。AI が利用者の承認を得て実行し、開いたブラウザで利用者本人がログインと承認をします。トークンは会話に出ず、以後は自動で更新されます。ブラウザの無い環境では、トークンの発行と `login --url` への貼り付けを利用者本人が行います。
- イシューの本文に本番データを貼らないでください（マスクするか ID だけを書きます）。

### 困ったとき

- `looptrack issue config` で、モード・プロジェクト・権限・トークンの取得元が分かります。サーバの URL が無いというエラーで止まるなら、設定の環境変数（`LOOPTRACK_API_URL` / `LOOPTRACK_PROJECT`）がそのシェルにありません。
- 参照したイシューを更新しないまま作業を終えようとすると、鮮度ガード（Stop フック）が止めます。調べたことや、やったことをコメントに残してください。
- トークン消費は、CLI の変更操作とフックが自動で送ります。**目印は文面ではなくコマンドです**。変更操作（起票・コメント・状態変更・verify の報告）の結果・標準エラー・`summary` の末尾に `looptrack issue usage attach <ID>` が出ていたら、示された ID ごとにそのコマンドをそのまま実行します。サーバの文面は利用者の言語で変わるので、特定の言い回しで探さないでください。Done / Canceled にするとき、その会話のトークン情報がイシューに無いと拒否するプロジェクトがあります（`usage.require_on_close`。CLI は自動で付けてやり直します）。
- トークン計測のコマンド: `looptrack issue usage show <ID>`（イシューの段階別。MCP は `issue_usage`）・`usage attach <ID>`（手動の付与）・`usage missing`（付いていない自分の AI 操作と充足率。MCP は `usage_missing`）・`usage report --since-last` / `--from D --to D`（期間の集計。MCP は `usage_report`）・`usage ledger list` / `usage ledger add <名前> --from-report r.json`（レポートの台帳。登録は取り消せない。MCP は `list_usage_ledger` / `add_usage_ledger`）・`usage requests`（画面から登録されたレポートの作成依頼。MCP は `list_usage_requests`）。
- `summary`（MCP は `project_summary`）に「トークンレポートの作成依頼」が出たとき、または「トークンレポートを作成して」と頼まれたときは、skill `token-report`（`.claude/skills/token-report`）の手順で集計 → 本文 → PDF → 台帳登録まで進めます（依頼の期間は `usage report --request N`、MCP は `usage_report` の `request_id`）。
- MCP のツール結果に注記が付くことがあります。導入が済んでいない（フック・CLI の導入済み通知が届いていない）か、配布物が古いことを知らせるものです。注記はツールの結果とは別の行に付き、`setup` ツールか更新のコマンドを示します（文面は利用者の言語で変わります）。付いていたら MCP の `setup` ツールを呼び、返ってきた手順を利用者の承認を得て実行してください（フック・CLI・案内文の導入。トークンの登録・AI の再起動・フックの承認は利用者が行います）。手元の状態は `looptrack issue installed --agent <claude-code|codex|copilot|other>` で確かめられます。
