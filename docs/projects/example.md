# example — 業務アプリの開発（例）

架空の業務アプリの開発プロジェクトで、課題管理（イシュー / 状態 / コメント）をどう運用するかを決めた文書です。共通の使い方は [../AI-GUIDE.md](../AI-GUIDE.md) にあります。
要件 → 設計 → 実装 → テストを 1 つのトラッカーで通します。AI が「着手 → 実装 → 検証 → クローズ → 次へ」を回すループ運用が前提です。

* 操作: `looptrack issue …`（MCP なら同じ名前のツール）。プロジェクトは `LOOPTRACK_PROJECT=example`
* サーバが強制するプロジェクト別ルール: [`deploy/rules/example.json`](../../deploy/rules/example.json)（下の「サーバが強制するルール」）
* この文書をサーバに登録すると、`looptrack issue guide` と MCP の `guide` が AI に返します。
  `looptrack project guide set example docs/projects/example.md --source docs/projects/example.md`

## 型（type）とラベル

| 型 | 用途 |
| -- | -- |
| `requirement` | 満たすべき要件。受け入れ条件をテスト可能な形で書く |
| `design` / `task` / `test` | 設計・実装・テスト。`--traces` で要件イシューを指す |
| `bug` | 不具合。見つけた時点で起票する |
| `epic` | 複数イシューの束。子は `parent` で指す |

* ラベル: 領域（`api` `web` `db` など）と案件（`CASE-101` の形）を入れます。
* **案件はラベルかブランチ名に `CASE-nnn` の形で入れてください。** トークンレポートの案件別の集計は、これで案件を決めます（`usage.case_pattern`）。

## 運用ルール

1. **作業は必ずイシューから始めます。** 不具合は見つけたらすぐ `bug` で起票します。原因や判断が分かった時点でコメントしてください（append-only）。
2. **未着手は Todo にまとめます。** Backlog は使いません。優先度は `priority` で表します。Backlog に置くと `next`・`ready` の候補から漏れるからです。
3. **Done の条件は、開発環境で動かして確かめたことです。** クローズのコメントに「動作確認: PASS（操作と確認した内容）」と書きます。
   調査や文書だけの課題のように動かして確かめるものが無ければ、「動作確認: 対象外（理由）」と書いてください。
4. **コメントを残さずに状態を進めないでください。** In Progress にするときは着手の方針を、Done にするときは修正と確認の結果を残します。
   `--comment` を使えば状態の変更と同時に残せます。
5. **受け入れ条件には、このイシューの作業で確かめられることだけを書きます。** 他の環境への反映やマージの依頼はチェックボックスに書きません。
   反映は別の手順で行います。未反映であることは、本文の注記に事実として書いてください。
6. **見つけた問題は、その場で `bug` として起票してから先へ進みます。** 会話や TODO コメントに抱えたまま次の実装を積み上げないでください。
   これはサーバが強制するものではなく、イテレーション規律とレビューで守ります。
7. **クローズの前にトークン情報を付けます**（AI の操作のとき）。CLI は拒否されたら `looptrack issue usage attach <ID>` を実行して 1 回やり直します。
8. **「## 検証コマンド」節を書いたイシューは、`looptrack issue verify <ID>` が全件成功してから Done にします。** 本文を直したら verify をやり直してください。
9. 待ちは `blocked_by` に書きます。クローズ済みは編集しません。蒸し返すときは新しく起票して参照します。
10. **受け入れ条件を起票の雛形のまま残さないでください。** `Done` にする前に「何をもって完了とするか」をテスト可能な形で書きます。
    記録や調査だけのイシューのように受け入れ条件を書けない場合は、理由を付けて上書きします。

## サーバが強制するルール（`deploy/rules/example.json`）

CLI・MCP・画面のどの経路から操作しても、サーバが次のものを拒否します。
CLI では `エラー: <次にすべきこと>` を出して exit 1 で終わります。文言は JSON の `message` で変えられます。

| ルール（キー） | 拒否するもの | 通し方 | 上書き |
| -- | -- | -- | -- |
| 使わない状態（`forbid_status`） | 起票・状態変更で `Backlog` | `Todo` か `In Progress` を選ぶ（運用ルール 2） | できない |
| 完了の記録（`done_requires_keyword`） | コメント（前置き・既存・同時）に「動作確認」が無い `Done`（起票も） | `close <ID> --comment "… 動作確認: PASS …"` | できない |
| コメント必須（`require_comment_before`） | コメント 0 件のまま `In Progress` / `Done`（起票時の状態指定も。`next` も同じ） | 先に `comment`、または `--comment` で同時に残す | できない |
| 反映依頼の受け入れ条件（`forbid_checkbox_pattern`） | チェックボックス行に「環境 × 反映・マージ × 依頼」がそろう記述（起票の本文・本文の更新・コメント。既存の行は対象外） | 本文の注記に事実だけを書く（運用ルール 5） | できない |
| トークン情報（`usage.require_on_close`） | AI の操作で `Done` / `Canceled` にするとき、その会話のトークン情報がイシューに無い | `looptrack issue usage attach <ID>` | 理由付きでできる |
| 検証コマンド（`verify.require_on_close`） | 「## 検証コマンド」節を持つイシューを `Done` にするとき、現在の本文に対する直近の verify が全件成功でない | `looptrack issue verify <ID>` | 理由付きでできる |
| 受け入れ条件（`acceptance.require_on_close`） | 「## 受け入れ条件」節を持つイシューを `Done` にするとき、節に中身のある行が 1 行も無い（起票の雛形・空のチェックボックス・「（未記入）」だけ） | `looptrack issue edit <ID>` で受け入れ条件を書く（運用ルール 10） | 理由付きでできる |

`usage` にはほかに次の設定があります。これらは拒否はしません。

* `case_pattern`（`CASE-\d+`）: トークンレポートの案件別の集計で、案件を決める正規表現です。イシューのラベルを見て、無ければブランチ名を見ます。
* `send_prompts`（この例では設定しない = 送らない）: トークン情報の区間に、人の指示文の先頭（作業名）を付けて送るかどうかです。

ルールの登録・確認・解除は管理者が行います。書式はサーバの設計書 DESIGN.md §5 にあります。

```bash
looptrack project rules set example deploy/rules/example.json   # 検査して保存する
looptrack project rules show example
looptrack project rules clear example
```

`rules set` はルール全体を置き換えます。ファイルに書かなかったルールは消えます。
ファイルで管理するなら、使うルールをすべてファイルに書いてください。
